The cost of change collapsed

Code agents as part of a history of how the cost of change shaped each era's interface to the machine.

That cost has collapsed, so software has become softer: material you keep reshaping, not a finished artifact you configure. (Ink & Switch, Malleable software, 2025)

Software is processes plus configuration. A GUI is one lossy view of that configuration.

The code is the interface

When editing code is cheap, code itself becomes the shared interface between the human and the model. (Karpathy, Software 3.0, 2025)

the code is the interface and i see with my ears. Steph, 2026-10-29

We make sounds by writing code, judge them by ear, and keep every iteration as a replayable trace. (live coding: TOPLAP, Alex McLean)

How it got here

2025

  • A breeding loop: each reply becomes the next prompt. The model is a generator.
  • Claude inside the SuperCollider interpreter, writing code into the document.

2026

  • An engine driven over OSC: every synth and pattern a file, every version kept.
  • Save while it plays and you hear it: hand edits join the loop.
  • Code as the material, and the interface. The terminal is primary.
  • Speed over accuracy.
  • A browser dashboard and an archaeological player for the history of making.

The model went from generator to collaborator in the files.

The engine

prompt→Claude Code (terminal)→library files→ engine (sclang, OSC)→scsynth→ears
  • Each synth and each pattern has its own file. Claude writes it; the human edits it too.
  • The engine validates, smoke-tests, versions and plays it.
  • Everything else (terminal, web UI, these slides) talks to it over OSC.

A synth is one file

library/synths/fmSweep/synthdef.scd

Prompt: “a fm synth with sweeping filters and detuning… make synth warm and add a hi tinkle… add a sub harmonic”

On its own, a synth is a sound: one note, held until you stop it.

Save to listen: saving over a playing file reloads it. Define to keep: a define makes a version. (Bret Victor, Inventing on Principle, 2012; Smalltalk's live image)

Mappings live in the code

  

    

      
No MouseX in a synth. It exposes params; the file declares which channel moves them:

      
map: (cutoff: [\mouseX, 150, 4000, \exp], res: [\mouseY, 0, 3.2, \lin])

      
Versioned with the synth. Change it in the code and the code wins.

Roles shift

  

    
human: author →judge and co-author
      Doesn't need to know the exact move, only whether it's right. Hand edits are the clearest message.

    
model: tool →collaborator
      Proposes moves, narrates them, learns from the human's edits.

    
artifact: product →trace
      What we keep is the history of intent, code and sound, not one final program.

  

  
Authorship is distributed: the human, the model and the stored history all shape each file. (Naur, Programming as Theory Building, 1985)

    Guardrails, not taste
    
  
      
    
    • Every define is smoke-tested (a live save isn't: it's heard at once): NaN fails it; silence, clipping, too loud, or not freeing are warnings.
      • 
    
    • A limiter on the master; mapped params are smoothed; input UGens are rejected.
      • 
    
    • Analysis views (spectrogram, MFCCs, stereo field) as a shared language.
      • 
    
    • The deliverable is a sound, not a program. The ear decides. No ratings, no stars, no “good” flags.
      • 
  
    

    



    
  
    Not decided yet
    
  
      
    
    • A topology vocabulary (resonator, feedback path, excitation, formant bank) to name moves and probes.
      • 
    
    • Comparing a version with the one before in descriptor terms: “brighter, more tonal”.
      • 
    
    • A static look at the graph before playing.
      • 
    
    • Seeded randomness, so a replay matches what was heard.
      • 
    
    • Annotation and search over the library, without turning into ratings.
      • 
  
    
  
    Spec comes after, not before: we find the vocabulary by making things.
